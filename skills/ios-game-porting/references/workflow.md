# Windows 到 iPhone / iPad 的完整流程

这是决策流程，不是所有游戏都通用的一键脚本。先查当前引擎发布说明、版本和游戏兼容性。2026-11 的 NX2Apple Windows 版本支持部分游戏构建和共享应用模式，具体工作流取决于版本和游戏；S2Arm 是另一套引擎，不能假定能直接使用 NX2Apple 的中间产物、着色器或进度。多游戏装一个宿主并不意味着不需要签名，签名方式和名额取决于实际安装方式。

## 1. 调查并建立可恢复基线

核对游戏名称、Title ID、地区、版本与 Build ID、基础游戏及更新/DLC、输入格式和所有权。检查设备机型、系统、空间、当前 App、真实签名后 bundle ID、证书能力及 AltStore 具体状态。预估构建和设备空间，保留源数据、校验摘要和现有存档。

检查工具自带的项目说明、现有配置、适用 AGENTS.md；记录源码/构建器版本、Windows 交叉工具、iOS SDK、Metal 工具链及工具链锁。工具版本、编译器、资源路径和配置变了可能使 shader 缓存失效。预编译不是 GPU 运行时 pipeline 全部现成；不要把构建进度或加载完成等同游戏验证。

Python 及依赖优先使用项目虚拟环境，实际解释器和路径先检测；不要硬编码其他人的电脑路径。设备不在、未信任或未解锁时，先做本地工作并在需要时让用户配合。

## 2. 确认构建方式

对可选择的 NX2Apple、S2Arm 或现有项目，核对官方支持列表和已有实际表现，说明兼容性与性能未知。区分：单游戏独立 IPA、共享宿主与游戏资料、以及旧版已有 IPA。能用现有构建产物就先检查，不承诺在不同引擎之间复用中间结果。

## 3. 处理输入与构建

使用当前项目支持的用户自有输入及配置。先调查主程序、版本、更新与 DLC、语言与配置；按引擎要求做提取、程序重写、shader 拆分与 Metal 编译、宿主构建、打包。每一步记录实际命令、日志、耗时、退出码、输出目录和摘要。构建长任务先检测是否已有进程，避免并行重做；保留可恢复的中间产物、SQLite 数据库及配套 WAL/SHM。失败时保留现场，按具体日志修复，不递归清理。

注意 Windows 的工具、路径编码和输入数量限制：某些版本的 Metal 工具在中文工作路径出错，必要时使用英文工作目录并保留日志；具体版本修复情况应再确认。旧工作流数据快照不可作为当前进度。

## 4. 核验 IPA 与外置数据

先确认输出是正确版本的完整程序，检查包结构、签名能力、体积、shader、主资源和 DLC 的真实布局，记录 SHA-256；小 IPA 可以依赖外置 ROMFS 等，不能仅根据 400 MB 判断游戏不完整。包拆分只按该宿主源码支持的路径操作：卡比某次需要外置 ROMFS 和 shader，火焰纹章某次仅外置 ROMFS；不能互套。

别轻率用历史失败测试包：比较哈希、补丁报告和已成功运行的日志。签名及设备安装按用户选择，先阅读侧载选择文档，安装前备份将被影响的 App 和数据。App 名额、到期时间和签名规则应结合账号与工具当前说明核实。

## 5. 真机部署与核验

用户确认设备连接解锁后查询签名后的真实 bundle ID 和应用的 Documents 路径，不跨游戏写入。优先用用户指定安装方式；大文件采用分块传输及可校验续传，校验已有前缀、完整长度与同算法哈希。设备端 SHA-1 与本地 SHA-1 比较，不要直接与 SHA-256 混比。日志、存档和游戏资源要归属正确 App；不要借用其他应用目录作为中转，除非用户明确同意。

对存档迁移，先备份源和目标并校验，核对游戏版本、目录布局、用户映射、文件清单和目标是否存在。迁移后设备端读回校验；用户亲自进入游戏确认最新进度。安装或切换前避免卸载导致容器丢失。需要签名、信任、开发者模式等交互时由用户在设备上完成。

## 6. 验收与交接

检查标题和实际场景、声音、字体/语言、手柄及触控、保存并重启读取、DLC、截图/切后台恢复；将“启动成功”与“完整通关”分开。记录帧率、同场景、功耗/热状态和画面设置；必要时验证 MetalFX 日志中的输入输出尺寸，输出分辨率不等于游戏内部渲染分辨率。

完成后提供用户可直接打开的入口、准确路径、可执行命令或复现步骤、校验清单、失败与未完成项、回退方式。涉及长任务就监控到结果或明确交接，不凭 ETA、解包百分比或文件存在宣告成功。
