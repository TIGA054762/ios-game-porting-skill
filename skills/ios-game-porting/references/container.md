# 容器方案：用一个宿主承载多个应用

Apple 免费个人账号的"活跃侧载应用数"通常只有 3 个（以账号、系统、工具当前规则为准）。独立安装每个 IPA 都会占用一个位置，游戏一多就不够用。容器方案把多个应用装进一个宿主，把名额留给真正必须独立安装的东西。

**容器不是绕过签名**，它改变的是签名的对象：签名落在宿主上，guest 在宿主进程内运行。因此宿主本身仍占 1 个名额、仍要续签，guest 的行为受宿主能力限制。

## 与引擎宿主（NX2Apple / S2Arm）的区别

| | 引擎宿主（NX2Apple、S2Arm 等） | 容器宿主（LiveContainer 等） |
|---|---|---|
| 运行对象 | 用该引擎构建的游戏 | 任意可被容器加载的 iOS 应用 |
| 覆盖面 | 只限该引擎支持的构建 | 游戏、工具、其他软件都可尝试 |
| 数据布局 | 由引擎决定（外置 ROMFS、DLC、shader） | 由被装入应用自身决定 |
| 兼容性风险 | 引擎与游戏版本是否匹配 | 应用所需 entitlement、扩展、JIT、权限未必可用 |

一个引擎宿主只能跑它自己的构建产物；容器能跑的东西更宽，但对单个应用能施加的能力更少（无法赋予容器本身不具备的 entitlement）。两者不互相取代，实际项目中常见的是"容器装游戏和工具，名额留给必须独立运行的宿主"。

## 前置检查

1. **宿主版本与能力**：确认当前版本是否支持所需特性（多开、Launch with JIT、Helper Process Support 等）。不同版本差异明显，需要时对照官方文档。
2. **名额现状**：清点已安装的侧载应用、各自签名工具与到期时间，判断哪些能转入容器、哪些必须留外。
3. **设备空间**：容器内每份 guest 数据都在宿主容器里，体积累加。迁移前先测可用空间，不要按单份数据估算。
4. **数据现状**：先备份将被迁移应用的 Documents（存档、外置资源、缓存、配置），记录哈希与体量。

## 数据布局

导入后宿主容器内典型结构（目录名以实际工具为准）：

```
Documents/Applications/<bundle-id>.app/     guest 应用本体
  LCAppInfo.plist                           guest 配置（含 LCDataUUID）
Documents/Data/Application/<UUID>/          guest 数据容器
  Documents/                                应用自己的 Documents
  Library/Preferences/                      偏好设置
  LCContainerInfo.plist                     容器信息
```

几个容易搞错的事实：

- **数据容器在 guest 首次启动时才创建**。导入完就去找容器目录会找不到，`LCAppInfo.plist` 里也没有 `LCDataUUID`。需要先在宿主里点一次启动，让它建容器——即使因缺资源立即退出也没关系。
- guest 的 Documents 路径形如 `.../Documents/Data/Application/<UUID>/Documents`，不是上一级目录。
- 应用本体目录（`.app`）不可当中转目录用，也不应往里写游戏数据。
- 宿主容器根目录下不应出现不属于任何 guest 的大文件。曾见到 14 GB 的镜像遗留在 `Data/Application/` 下，既不参与运行，也没有任何提示地占着空间。

## 迁移流程（独立版 → 容器）

1. **备份源**。从独立版的 Documents 拉取存档、外置资源（ROMFS、DLC、shader 缓存）、配置，逐文件校验。
2. **导入 IPA**。用宿主的导入入口选择 IPA；导入后确认 guest 目录名——签名后的 bundle ID 可能带后缀，不要沿用旧值。
3. **首启建容器**。启动一次，让宿主生成数据容器。
4. **读容器 UUID**。从 `LCAppInfo.plist` 读 `LCDataUUID`（或 `LCContainers[0].folderName`），不要硬编码。
5. **先小后大**。先写存档、配置文件、小的 shader 归档，验证应用能识别；再写十几 GB 的主资源。
6. **大文件用临时名**。先写 `.part`，设备端校验哈希后再重命名为正式文件名，避免中断留下"看似完整"的碎文件。
7. **逐文件校验**。设备端 `get_file_hash`（SHA-1）与本地同算法哈希对比，不要与设备端 SHA-256 混比。
8. **启动验证**。先确认能进应用，再确认能读档；两步都过了才能考虑删除独立版。
9. **删除独立版**。必须得到用户逐项确认；删除前确认容器内已校验通过且能读档。

## 传输与校验的工程细节

- **方向差异很大**：设备→电脑读方向单流常见 5–8 MB/s；电脑→设备写方向可以到 16–19 MB/s。估时要分开算，不要用平均速率。
- **多连接不一定更快**：读方向开多条连接可能被设备中断，表现为会话挂死或空读，最后只能重来。优先单连接稳定跑，必要时才少量分段并加重试。
- **同一文件只能有一个写入者**。两个进程同时写同一目标会造成哈希不符、文件污染，而且从结果上很难分辨谁写坏了。
- **Windows 没有 `os.pwrite`**。需要按偏移写入时，用每任务独立文件描述符加 `lseek` + `write`，或者保证顺序追加。直接调 `os.pwrite` 会报 `AttributeError`，而且读回来的数据根本没落盘——进度看着在动，文件其实没变。
- **不要相信"进度条在动"**。计数器、文件长度、稀疏分配都可能骗人，最终以整文件哈希与设备端读回为准。
- **大量小文件很耗时**。六千多个文件每个都要多次往返，实际耗时远超按体积估算。先排大件，小件放最后。
- **AFC 不能跨容器复制**。独立版到容器必须经电脑中转，电脑上那份同时也是备份，不是重复劳动。
- **区间哈希要谨慎**。设备端的区间哈希接口在大量请求下可能挂起，不是所有设备都适合逐块验证；优先整文件哈希加抽样。

## 兼容性核查

不是所有应用都能在容器里正常工作。遇到下列特征，先验证再承诺：

- **需要宿主不具备的 entitlement**：例如提高内存上限、特定 Metal 能力。
- **需要 JIT**：容器的"免 JIT 模式"是让 guest 不需要 JIT，不等于给 guest 提供 JIT。要 JIT 时通常是外部先把 JIT 赋予宿主进程，再让 guest 以 JIT 模式启动。
- **带 app 扩展**：扩展能否随宿主一起被保留取决于签名工具。同一 IPA 用工具 A 装可能丢扩展，用工具 B 装则完整，这类问题只能实测，不能按工具名气推断。
- **依赖特殊文件访问**：部分应用会拒绝被外部读取容器（例如 `InstallationLookupFailed`），这类应用不适合做自动化迁移。

## 验收清单

- [ ] 宿主内 guest 目录与 UUID 已确认，不是凭猜测写入
- [ ] 存档、配置、外置资源均有设备端读回哈希
- [ ] 应用能启动，且能读到迁移前的最新存档
- [ ] 容器内无多余的大文件残留
- [ ] 用户已确认可以删除独立版，删除后容器副本仍可启动
- [ ] 记录了宿主版本、签名工具、到期时间与回退方式
